`$ARGUMENTS` 의 첫 토큰이 에픽 키다. 두 번째 토큰이 숫자면 동시 실행 상한이고, 없으면 `2` 로 둔다.

이슈 하나를 준비하는 절차는 `.claude/commands/wt.md`, 마감하는 절차는 `.claude/skills/wt-done/SKILL.md` 에 있다. **이 명령은 그 둘을 다시 쓰지 않고 호출한다.**

## 코드를 쓰지 않는다

구현·테스트·코드리뷰·커밋은 전부 하위 세션의 몫이다. 이 세션이 파일을 고치기 시작하면 나머지 일감의 회수가 멈춘다. 하는 일은 다섯 가지뿐이다 — 조회 · 계획 · 팬아웃 · 회수 확인 · 머지 순서 지시.

**메인 체크아웃에서 실행한다.** `develop` 은 여기에만 체크아웃돼 있고, `/wt` 는 이 세션을 옮기지 않는다.

## 1. 환경 확인

```bash
test "${HERDR_ENV:-}" = 1
```

실패하면 herdr 밖이라고 알리고 중단한다. `/wt` 가 herdr 를 요구한다.

## 2. 에픽과 하위 일감을 조회한다

에픽 자체는 `getJiraIssue` 로 키로 직접 조회해 **요약과 현재 상태**를 얻는다. 요약은 4절 계획 표에, 상태는 8절 완료 판정에 쓴다 — 에픽이 이미 완료면 전환하지 않는다.

하위 일감은 **두 질의를 모두 실행한다** — 하나만 보면 클라 일감을 서버가 가져간다.

**① 미완료 하위 전체 — 보고용**

```
parent = <에픽키> AND status != 10092 ORDER BY key ASC
```

**② 팬아웃 후보 — 담당이 나이거나 미지정인 것만**

```
parent = <에픽키> AND status != 10092 AND (assignee = currentUser() OR assignee IS EMPTY) ORDER BY key ASC
```

**펜스 안에 주석을 넣지 않는다.** JQL 에 `#` 주석 문법이 없어 블록째 복사하면 실패한다.

두 질의 모두 2026-09-01 에 MGR-171 로 실측했다 — ①이 3건, ②가 1건이었다. 차이 2건은 클라 담당이다.

**①에서 ②를 뺀 나머지를 팬아웃하지 않는다.** 목록에 「타 담당」으로 표시만 하고 넘긴다. 그 일감이 서버 몫이라고 판단되면 담당 변경은 사용자가 정한다.

**필터를 담당자 이름으로 쓰지 않는다.** `currentUser()` 를 쓴다 — 클라 담당은 사람이 여럿이라 이름을 열거하면 새 담당자가 서버 후보로 들어온다.

`status != 10092` 처럼 **상태는 id 로 질의한다.** 이 사이트의 JQL 은 한글 값에 오류 없이 0건을 반환한다.

## 3. 직렬화 요인을 판정한다

**먼저 ②의 미지정 건을 거른다.** 요약이 `클라 -` 로 시작하면 「타 담당」으로 옮긴다. `assignee IS EMPTY` 가 담당 미지정 클라 일감을 서버 후보로 끌어온다 — 클라 이슈의 요약 관례가 그 접두어다 (`wt-done` 2단계가 만든다).

남은 후보의 **본문을 읽는다.** 요약만으로는 아래를 알 수 없다.

| 요인 | 왜 병렬이 깨지나 |
|---|---|
| DB 스키마·패치 | `patches/` 의 적용 순서와 manifest 가 한 벌이다. 두 worktree 가 같은 버전 디렉터리에 패치를 넣으면 순서가 정해지지 않는다 |
| proto 변경 | 원본이 한 벌이다 — `game-server/build/protobuf/src/` |
| 같은 파일·같은 패키지 | 뒤에 머지되는 쪽이 충돌을 푼다 |
| 선행 의존 | 뒤 일감이 앞 일감의 심볼을 쓴다. 앞이 머지된 뒤에 브랜치를 만든다 |

**요인은 이슈 쌍 사이에서 본다.** 같은 요인을 공유하는 것들만 한 직렬 사슬로 묶고, 나머지는 병렬로 둔다 — 이슈 하나를 「직렬이다/아니다」로 판정하면 두 방향으로 틀린다. 서로 무관한 패치 건과 proto 건이 한 사슬에 묶여 병렬이 사라지고, 각각은 무해하지만 같은 파일을 만지는 쌍이 「요인 없음」으로 함께 병렬 그룹에 들어간다.

판정 근거를 이슈키와 함께 적는다 — 「독립」이라고만 적으면 다음 그룹에서 근거를 다시 만들 수 없다.

「저쪽이 영향받는다」고 판정했으면 **저쪽 코드에서 심볼을 grep 한다.** 판정 근거를 이슈 본문의 서술에만 두지 않는다.

## 4. 계획을 한 번에 승인받는다

`AskUserQuestion` 한 번으로 묶는다. 표에 담을 것:

- 하위 일감 전체와 담당(②에서 빠진 것은 「타 담당」으로)
- 그룹별 실행 순서와 각 그룹의 병렬 수
- 일감별 직렬화 요인 또는 「독립」 판정 근거
- **팬아웃 전에 확인한 사실과 확인하지 못한 것**

**묻는 것은 여기 한 번이다.** 승인 뒤에는 그룹 경계마다 되묻지 않는다. 단 3번 판정이 틀렸다는 것이 실행 중에 드러나면 멈추고 다시 묻는다.

**마감 단계의 정지는 이 승인과 별개다.** `wt-done` 0단계가 하위 세션에서 다시 묻고, 그 4단계는 권한 프롬프트를 띄운다. 7절이 다룬다.

계획을 요약만 놓고 「진행할까요?」로 묻지 않는다. 각 일감에 어떤 명령이 실행되고 무엇이 바뀌는지 적는다.

## 5. 그룹을 팬아웃한다

**그룹마다, 팬아웃 전에 로컬 `develop` 을 원격에 맞춘다.**

```bash
git fetch origin
git merge --ff-only origin/develop
```

`herdr worktree create --base develop` 은 **로컬** `develop` 에서 갈라진다. 하위 세션의 머지는 `origin/develop` 에만 반영되므로, 맞추지 않으면 그룹이 넘어갈수록 격차가 누적된다 — 2026-09-01 실측에서 이 체크아웃이 이미 3 커밋 뒤처져 있었다(`git rev-list --left-right --count develop...origin/develop` 가 `0	3`). 직렬 그룹의 뒤 일감이 앞 일감의 머지 이전에서 갈라지면 직렬화가 값을 하지 못한다.

**`--ff-only` 가 실패하면 멈추고 묻는다.** 로컬 `develop` 에 원격에 없는 커밋이 있다는 뜻이라 임의로 처리하지 않는다.

그 뒤 그룹의 일감마다 `.claude/commands/wt.md` 의 절차를 그대로 수행한다. 브랜치명·라벨 규칙, `--base develop`, 완료 이슈 전환 가드가 모두 그 문서에 있다.

**`wt.md` 는 「에이전트에 프롬프트를 넣지 않는다」고 정한다. 이 명령은 그 규칙에 예외를 둔다** — 사용자가 각 하위 세션을 직접 몰지 않으므로 첫 지시를 넣는다.

```bash
herdr agent prompt <에이전트이름> '<첫 지시>' --wait --until working --timeout 30000
```

**`agent_prompt_stalled`·타임아웃을 제출 실패로 읽지 않는다.** `--wait` 은 **제출 뒤** 상태 변화를 기다리는 것이라 오류가 나도 프롬프트는 이미 들어가 있다 (`--help` 명시). 다시 보내면 하위 세션이 같은 작업을 두 번 시작한다 — `herdr agent read` 로 상태를 먼저 본다.

첫 지시에 담을 것:

- 이슈 키와 「이 이슈만 해결한다」
- **push 와 PR 생성까지 한다. 머지하지 않는다. 머지 지시를 기다린다**
- push 전에 코드리뷰를 수행한다 (CLAUDE.md 의 리뷰 의무)
- 검증 기준선은 변경 전후 비교다 — 변경 전에 먼저 측정한다
- 끝났으면 PR 번호를 보고하고 대기한다 — 다만 회수는 그 보고에 기대지 않는다. 6절이 `gh` 로 직접 얻는다

**상한을 넘겨 띄우지 않는다.** 한 그룹이 상한보다 크면 상한 단위로 나눠 순차 처리한다.

## 6. 회수를 확인한다

```bash
herdr agent wait <에이전트이름> --timeout 1800000
```

**`--until` 을 붙이지 않는다.** 생략하면 `idle`·`done`·`blocked` 를 모두 잡는다 (`--help` 명시). `--until idle` 로 좁히면 권한 프롬프트나 질문으로 멈춘 에이전트가 `blocked` 라 매칭되지 않고 타임아웃까지 통째로 흘러간다.

타임아웃으로 종료코드 `1` 이 나오면 30분 동안 상태가 변하지 않은 것이다. 아래 두 조회로 살아 있는지 판정하고, 판단이 서지 않으면 사용자에게 넘긴다.

**멈춘 것과 끝난 것을 상태로 구분하지 않는다.** 산출물을 본다.

```bash
gh pr list --head <브랜치> --state all --json number,state
```

- 빈 배열 `[]` 이면 PR 이 없다 (종료코드는 `0` 이다 — 없는 브랜치에서도 그렇다)
- `OPEN` 이면 지시대로 멈춘 것이다. 7절로 간다
- `MERGED` 면 하위 세션이 지시를 어기고 머지한 것이다. **멈추고 보고한다** — 직렬 순서가 이미 깨졌다

**`--state all` 을 생략하지 않는다.** 기본값이 `open` 이라 이미 머지된 PR 이 「PR 없음」과 구분되지 않는다.

**여기서 `mergeable` 을 가져오지 않는다.** `gh pr list` 는 그 필드를 채우지 않는다 — 같은 PR #119 가 `pr list` 에서는 `UNKNOWN`, `pr view` 에서는 `MERGEABLE`·`CLEAN` 이었다 (2026-09-01 실측). 여기서 읽으면 항상 `UNKNOWN` 이라 판정이 무의미하다. 필요한 곳은 7절이고, 최종 판정은 `wt-done` 0단계가 한다.

PR 이 없으면 `herdr agent read <에이전트이름>` 으로 무엇에 막혔는지 본다. 막힌 것이 사용자 판단이 필요한 것이면 그대로 보고한다 — 대신 답하지 않는다.

`herdr agent prompt --wait` 는 턴을 추적하지 않는다. 이미 working 인 에이전트에 걸면 **직전 턴의 종료가 매칭될 수 있다** (`--help` 명시). 그래서 완료 판정은 항상 PR 로 한다.

## 7. 머지 순서를 지시한다

**머지 순서는 이 세션이 정한다.** 하위 세션이 스스로 머지하면 직렬 그룹의 순서가 깨진다.

순서대로 한 세션씩 지시한다.

```bash
herdr agent prompt <에이전트이름> 'wt-done 으로 마감해줘'
```

`wt-done` 이 그 세션에서 사전 점검 → 머지 → Jira 완료 → worktree 제거를 수행하고 **그 세션을 종료한다.** 4단계가 세션을 끝내므로 이 세션에서 대신 실행하지 않는다.

### 마감은 그 pane 에서 두 번 멈춘다

지시했다고 진행되지 않는다. `wt-done` 0단계가 `AskUserQuestion` 으로 승인을 묻고, 4단계의 `herdr worktree remove` 는 어느 allowlist 에도 없어 권한 프롬프트를 띄운다. 둘 다 **하위 pane** 에 뜨는데 사용자는 이 pane 을 보고 있다.

```bash
herdr agent wait <에이전트이름> --timeout 600000
```

멈추면 `herdr agent read <에이전트이름>` 으로 무엇을 묻는지 읽어 **그대로 사용자에게 넘긴다.** 대신 답하지 않는다 — 그 승인은 되돌릴 수 없는 단계에 대한 것이다.

### 마감 완료는 PR 로 판정한다

세션이 종료되므로 `herdr agent wait` 으로 끝을 기다리지 못한다. 6절에서 얻은 PR 번호를 쓴다.

```bash
gh pr view <번호> --json state,mergedAt
```

`MERGED` 가 된 뒤에 다음 세션에 지시한다. `herdr agent wait` 이 `agent_not_found`·종료코드 `1` 을 내는 것도 그 세션이 사라졌다는 신호다 (2026-09-01 실측). **둘을 함께 본다** — 에이전트만 사라지고 PR 이 `OPEN` 이면 마감이 중간에 끊긴 것이다.

### 뒤 일감의 리베이스

앞이 머지되면 뒤 브랜치는 뒤처진다. 다만 **뒤처졌다는 것만으로 리베이스하지 않는다** — 충돌이 없으면 그대로 머지된다.

```bash
gh pr view <번호> --json mergeable,mergeStateStatus
```

**`pr list` 가 아니라 `pr view` 로 조회한다** — list 는 이 필드를 채우지 않는다.

- `CONFLICTING` 이면 그 세션에 지시한다 — 리베이스 → **재검증** → `git push --force-with-lease`. PR 이 이미 열려 있어 push 하지 않으면 리베이스가 PR 에 반영되지 않는다
- `UNKNOWN` 이면 판정하지 않는다. 몇 초 뒤 한 번 다시 조회하고, 그대로면 마감을 지시한다 — `wt-done` 0단계가 같은 판정을 다시 한다. 2026-09-01 실측에서 하루 지난 PR #106 이 `pr view` 에서도 `UNKNOWN` 이었다
- `MERGEABLE` 이면 그대로 마감을 지시한다

## 8. 다음 그룹으로 넘어가고, 에픽을 판정한다

그룹이 남아 있으면 5번으로 돌아간다. 다 끝나면 2번의 ① 질의를 **다시 실행한다.**

- 0건이면 에픽 완료 전환을 제안한다. 전환 id 표는 `.claude/skills/wt-done/SKILL.md` 2단계에 있다
- 타 담당만 남았으면 그 사실을 보고하고 에픽은 열어 둔다 — 클라 잔여가 있는 에픽을 닫지 않는다
- 새 하위 일감이 생겼으면 3번으로 돌아간다

## 자주 틀리는 것

| 이렇게 한다 | 왜 |
|---|---|
| 후보 질의 없이 ① 전체를 팬아웃한다 | 클라 담당 일감에 worktree 가 붙는다. MGR-171 은 3건 중 2건이 그렇다 |
| 담당자를 이름으로 필터한다 | 클라 담당이 여럿이다. `currentUser()` 를 쓴다 |
| 요약만 보고 독립이라 판정한다 | DB 패치·proto 는 본문에만 있다 |
| `agent wait` 에 `--until idle` 을 붙인다 | `blocked` 를 버려 멈춘 에이전트를 놓친다. 생략하면 셋 다 잡는다 |
| 상태로 완료를 판정한다 | 물어서 멈춘 것도 idle 이다. PR 로 판정한다 |
| `gh pr list` 에 `--state all` 을 빼먹는다 | 기본값이 `open` 이라 이미 머지된 PR 이 「PR 없음」으로 보인다 |
| `agent prompt` 가 오류를 내서 다시 보낸다 | 제출은 이미 끝났다. 하위 세션이 같은 작업을 두 번 시작한다 |
| 요인을 이슈 하나 단위로 판정한다 | 쌍 사이의 성질이다. 무관한 것이 묶이거나 같은 파일을 만지는 쌍이 병렬로 간다 |
| 하위 세션에 머지까지 맡긴다 | 직렬 그룹의 순서가 깨진다 |
| 이 세션에서 `wt-done` 을 실행한다 | 4단계가 실행한 세션을 종료한다. 메인 체크아웃 세션이 죽는다 |
| `git fetch` 없이 다음 그룹을 팬아웃한다 | 로컬 `develop` 이 뒤처진 채로 갈라진다. 직렬화가 값을 하지 못한다 |
